# Anantdv App Store

A private Next.js app distribution portal for company customers. Administrators create individual accounts, assign apps to companies, publish binaries and feature notes, and manage version history.

## Included

- Next.js App Router with server-rendered catalog and admin pages, TypeScript, and responsive layouts.
- SQLite local database with Prisma migrations; binaries stored privately on disk.
- Roles: customer, viewer, administrator. Customers download their company's assigned published versions; viewers browse all active apps without download access; admins manage everything.
- Latest release and older-version downloads, plain-text feature notes, file sizes, checksums, and publication controls.
- Signed access tokens, hashed rotating refresh tokens, immediate account/session revocation, mandatory admin authenticator MFA, one-use recovery codes, password-change flow, throttling, and audit history.
- Validated environment configuration and a shared browser API function in `src/lib/api-client.ts`.

## Quick Setup (After Cloning from GitHub)

1. **Clone and install dependencies**:
   ```bash
   git clone <your-repo-url>
   cd panaya_app_store
   npm install
   ```

2. **Configure environment & secrets**:
   ```bash
   npm run setup:env
   ```
   > 🔒 **Security Note**: All credentials, tokens, session keys, SQLite database files (`data/`), and uploaded app binaries are ignored by `.gitignore`. The **only** place application secrets exist is your local `.env` file, which is never committed to GitHub.

3. **Initialize database schema**:
   ```bash
   npm run db:generate
   npm run db:migrate
   ```

4. **Create initial admin account** (optional: set `BOOTSTRAP_ADMIN_EMAIL` & `BOOTSTRAP_ADMIN_PASSWORD` in `.env`):
   ```bash
   npm run admin:create
   ```

5. **Start development server**:
   ```bash
   npm run dev
   ```
   Access locally at `http://localhost:3000` or from network devices at `http://<your-ip>:3000`.

Set these values in your private `.env` before creating your first administrator:

```dotenv
BOOTSTRAP_ADMIN_EMAIL=your-admin@your-company.com
BOOTSTRAP_ADMIN_NAME=Your Name
BOOTSTRAP_ADMIN_PASSWORD=your-own-unique-password-of-at-least-12-characters
```

This is an example format, **not a working password**. Then run:

```powershell
npm.cmd run admin:create
npm.cmd run dev
```

Open [http://localhost:3000](http://localhost:3000). Sign in with the administrator credentials you supplied, scan the authenticator QR code, verify a code, and save the ten recovery codes. Remove `BOOTSTRAP_ADMIN_PASSWORD` from `.env` after bootstrap. There are no default login credentials or public registration.

## Give customers an app

1. In **Companies**, create a customer company.
2. In **Users & roles**, create a customer linked to that company. Share the generated temporary password privately; the user must replace it at first login.
3. In **Apps & releases**, create an app and upload a binary with its version label and feature notes.
4. Publish the release immediately, or keep it as a draft and publish later.
5. Open the company's management page and assign the app.
6. The customer can now sign in and download the latest and previous published releases. The latest version is determined by publication time, not version text.

Create viewer accounts to give catalog and release-note visibility without downloads. All admin accounts require MFA. Company/app/user disabling and app-assignment removal take effect on the next request. Role, email, company, password, and MFA changes revoke the affected user's sessions.

An app assignment covers **all published versions** of that app. One binary belongs to each release. To offer different binaries for different platforms, create separate apps. Feature notes are text, not HTML.

## Configuration

| Variable | Purpose / default |
| --- | --- |
| Host / origin | Detected per request; no `APP_ORIGIN` configuration is needed (legacy values are ignored) |
| `DATABASE_URL` | Local SQLite URL, `file:./data/payana.db`; relative paths resolve from project root |
| `UPLOAD_DIR` | Private persistent folder, `./data/uploads`; must remain outside `public` |
| `UPLOAD_MAX_MB` | Upload limit in MiB, default 250, range 1–1024 |
| `UPLOAD_EXTENSIONS` | `apk,aab,ipa,exe,msi,dmg,pkg,zip,tar.gz` |
| `TOKEN_SECRET` | Random secret of at least 32 characters; generated by setup |
| `MFA_ENCRYPTION_KEY` | 32-byte random AES key encoded as 64 hex characters; generated by setup |
| `ACCESS_TOKEN_SECONDS` | Default 900 (15 minutes), range 60–3600 |
| `REFRESH_TOKEN_SECONDS` | Default 604800 (7 days), range 3600–2592000 |
| `TRUST_PROXY` | Default false; set true only when your proxy overwrites `X-Forwarded-Host`, `X-Forwarded-Proto`, and `X-Forwarded-For` |

Secrets are server-only. Never prefix them with `NEXT_PUBLIC_`. Keep the MFA encryption key when restoring a backup; without it enrolled authenticator secrets cannot be decrypted. Changing the signing key ends existing access-token validity. Refresh families expire seven days after login; refreshing does not extend that maximum lifetime.

Use a current browser with Web Locks support (current Edge, Chrome, Firefox, or Safari). The shared refresh coordinator serializes renewal across tabs to avoid refresh-token reuse. Credential verification and session/challenge creation bind to the account's security version, so a concurrent administrator reset cannot preserve an earlier password proof. Attempt admission is transactional, including MFA attempts. JSON API bodies are capped at 64 KiB while being read; multipart binary uploads use their separate configured limit.

Downloads use authenticated server routes, attachment headers, and `private, no-store` caching. File keys are generated server-side. Uploads stream to temporary files with size enforcement, checksum computation, and cleanup on failure. Installer signing and malware scanning are not included; publish only binaries you have verified.

## Production

Deploy **one Node.js server** with persistent disk and an HTTPS reverse proxy. This local-storage configuration is intended for a single server; ephemeral serverless storage and multiple replicas are not supported.

1. Provision private persistent database/upload directories outside web-served folders and restrict their permissions to the application service account.
2. Set persistent storage paths and production secrets in the environment. No domain or origin setting is required.
3. Install, generate the client, apply migrations, and build:

```powershell
npm.cmd ci
npm.cmd run db:generate
npm.cmd run db:migrate
npm.cmd run build
npm.cmd start
```

The same production build runs on localhost, LAN IPs, or a production domain. Login cookies are HttpOnly and SameSite=Strict; Secure is enabled per request when using HTTPS, allowing local HTTP access with `npm start`. Mutation requests must match the current request origin, including protocol and port.

Behind an HTTPS reverse proxy, set `TRUST_PROXY=true` at runtime and configure the proxy to overwrite `X-Forwarded-Host` with the public host (including any non-default port), `X-Forwarded-Proto` with the public protocol, and `X-Forwarded-For` with the client IP. Keep the Node port reachable only through that proxy. Direct local/LAN access uses the default `TRUST_PROXY=false`. Configure proxy upload/body limits above your selected file limit plus multipart overhead, upload timeout, and download-stream timeout. Do not cache authenticated pages, API responses, or downloads in the proxy/CDN.

The content security policy allows inline script/style needed by Next.js; development alone permits eval for React debugging. Pages cannot be framed. No external fonts, image hosts, or analytics are required.

Build once, then run locally or deploy the build with the appropriate runtime secrets and storage configuration:

```powershell
npm.cmd run build
npm.cmd start
```

Open `http://localhost:3000` or `http://<your-ip>:3000` locally. No temporary HTTPS origin override is needed.

## Backup and recovery

Stop the service before taking a simple file-copy backup. Copy the SQLite database, the **entire uploads directory**, and the private environment secrets together to protected storage. If using an online SQLite backup mechanism, coordinate it with uploads so both represent the same point in time. Restore them together, retain the original MFA key, apply pending migrations, and restart. Test restores periodically.

Users who forget a password need an admin-issued temporary-password reset. An admin who loses an authenticator can sign in with a saved one-use recovery code. Another administrator can reset their MFA in **Users & roles**. Keep at least one recovery code safely stored and preferably a second admin account; the UI does not let an administrator reset their own MFA. If all administrators lose both authenticator access and recovery codes, recovery requires an authorized operator working directly with the private database; there is intentionally no public MFA bypass endpoint.

Database/session/audit records are retained for traceability. For long-running production installations, schedule retention/archiving appropriate to your operating requirements; there is no automatic audit-retention job in this initial version. Unpublish releases instead of deleting historical records.

## Verification

```powershell
npm.cmd test
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run test:e2e
```

Unit/integration tests initialize a separate `data/test.db`. Browser tests initialize `data/e2e.db`, private `data/e2e-uploads`, use port 3001, and run in an installed Microsoft Edge browser. Test-only credentials never seed the normal application database. Browser screenshots are written to `artifacts/`; failure traces and screenshots go to `test-results/`. To use bundled Chromium instead, remove `channel: 'msedge'` in `playwright.config.ts` and run `npx playwright install chromium`.

For restricted Windows environments where the browser runner cannot stop its subprocess, `PAYANA_E2E_EXTERNAL=true` skips test-server startup/cleanup. Start a separately managed dev server on port 3001 using the `DATABASE_URL`, `UPLOAD_DIR`, test signing key, MFA key, and `PAYANA_E2E=true` values in `playwright.config.ts`, then run the tests with that flag. Use this mode only with the dedicated test database, never the normal application database. The complete browser suite was verified in this managed-server mode.

Security checks cover company isolation, viewer download denial, admin MFA, recovery/TOTP reuse, password changes, token rotation/reuse, revoked sessions, upload limits and cleanup, database uniqueness, last-admin protection, and actual browser login/download/upload flows.

## Source map

- `src/config/env.ts`: validated global environment configuration.
- `src/server/auth/`: credentials, principals, sessions, tokens, MFA, login challenges, and throttling.
- `src/server/services/`: authorized company/user/app/release operations.
- `src/server/storage.ts`: private streaming upload/download operations.
- `src/app/api/`: allowlisted authentication/admin handlers and authenticated binary downloads.
- `src/app/catalog/`: server-rendered library and version history.
- `src/app/admin/`: company, user, app, release, and activity management.
- `prisma/`: schema and migrations.

Framework setup follows the [Next.js installation documentation](https://nextjs.org/docs/app/getting-started/installation) and [Prisma SQLite adapter documentation](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/sqlite). TOTP uses [OTPAuth](https://github.com/hectorm/otpauth).
